## 一句话概括

让一个会用工具的 LLM 充当"奖励工程师"，为一类相关的协作多智能体场景写出同一份奖励代码。写好后冻结，不做任何修改，直接拿去训练设计阶段没见过的新场景。

## 核心方法

- **按任务族设计奖励**：场景分成开发集和留出集。LLM 只能看到开发集，留出集全程对它隐藏，用来检验奖励能否迁移。
- **自主找证据**：Eureka 这类方法只给 LLM 固定格式的训练统计。GARDEN 让 LLM 自己决定看什么：环境与算法源码、训练曲线、原始轨迹、checkpoint，还能自己写分析脚本，用少量试训练（probe）验证草稿奖励。
- **固定的部分**：学习算法和最终选奖励的规则都不变。候选奖励多代迭代，最后选在所有开发场景上相对默认奖励平均提升最大的那份。

## 关键结果

- Overcooked 的两个未见厨房布局上，任务回报比环境自带奖励分别高 58.2% 和 52.5%。
- SMAX 的两个未见战斗场景上，平均胜率从 51.0% 提到 89.9%。
- 候选数和试训练预算相同时，固定诊断反馈只有 84.2%，Eureka 式反思只有 79.2%，都低于 GARDEN。

## 为什么值得关注

LLM 写奖励的工作大多在单一场景里设计、单一场景里评估，换个布局或换个队伍配置往往要从头再搜。这篇论文把评估目标改成"奖励本身能否迁移"，并说明放手让 LLM 去查原始行为证据，比喂给它预设好的统计更能发现协作失败的原因。对机器人、车队这类配置经常变化的协作系统，这能明显减少反复手工设计奖励的成本。
