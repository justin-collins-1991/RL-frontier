## 一句话概括

SPILLWAY 不靠大模型做放行决策，而是根据工具返回的"类型化字段"判断一个动作的目标（收件人、账户、文件）是否可信，给工具型 Agent 提供一道确定性、可审计的提示注入防线。

## 核心方法

关键观察：合法目标（邮件发件人、转账收款账户）通常出现在工具返回的结构化字段里，而注入指令只能藏在正文、描述等自由文本中。据此拆成两道关卡：

- **出口闸门**：Agent 发起有副作用的调用时，如果目标既不是用户任务里提到的，也不是只读工具在身份类字段中返回的（或不符合固定的委托规则），就直接拒绝。整个过程只是查集合，不调用模型，换哪个底座模型结果都一样。授权、删除类操作要求更严格。
- **入口清洗**：模型读取工具输出前，用固定规则剔除伪造的对话轮次和类似指令的片段，并把剔除内容留作证据。
- **本地裁判**：只复核被拒绝的调用，用来恢复用户真正委托的操作；但如果目标出现在被剔除的片段里，裁判无权放行。

## 关键结果

- 在 AgentDojo 上测了 3 个底座模型，其中一个跑了 7 个任务套件：标准模板注入的攻击成功率全部为 0，同时效用和综合分在所有防御中最高。
- 伪造聊天模板攻击（ChatInject）同样为 0；面对强化学习攻击器 PISmith，平均攻击成功率只有 0.007。
- 不会因为防御触发底座模型重跑，几乎不增加额外的模型调用；MELON、Progent、DRIFT 等对比方法在多数格子里仍会泄漏。

## 为什么值得关注

现有防御大多让大模型来判断"放不放行"，而这个模型本身就可能读到并被攻击文本误导，还会增加推理成本。SPILLWAY 把安全底线交给确定性规则，模型只负责"恢复效用"，不负责"守住安全"。这种分工能跨模型复用、便于审计，对处理邮件、文件、支付的个人 Agent 落地很有参考价值。它的局限是只管动作发给谁，不管发出去的内容是否被注入篡改。
