## 一句话概括

作者在 verl 里把 MXFP8 同时用在训练端和采样端，在 B200 上实测了三件事：两端对齐能带来多少一致性，什么条件下真的更快，以及权重同步会以哪些方式出错。

## 核心方法

- **共享网格同步**：每次优化器更新后，用训练端自己的量化器重新量化权重，再发给 vLLM/SGLang 采样端，让两端用逐字节相同的 FP8 权重，不需要校准，也不需要离线转换。
- **盈亏平衡模型**：把每个阶段的耗时拆成"每个 micro-batch 的固定开销 + 每个 token 的开销"，由此算出 MXFP8 开始划算的 token 数门槛。
- **正确性规范**：列出权重同步必须满足的 7 个条件，并在运行时对在线引擎做检查，专门用来发现不报错的静默故障。

## 关键结果

- 对 MXFP8 训练端来说，网格对齐的采样端比 BF16 采样端更一致：一半线性层对齐时，训练与采样之间的 KL 降低 11%，全部对齐时降低 16%。在 MoE 模型上，两端网格不一致会让 KL 从第一步起就翻倍。不过如果 KV cache 没有量化，全程 BF16 的一致性仍然高 2.5–10 倍。
- 速度方面，稠密模型只有在每个 micro-batch 超过约 4.5k token 时才划算，多出来的时间主要是 GPU 在等 host。端到端结果：MoE 的单步时间减少 10.7%，生成时间减少 24%；短序列的稠密任务反而慢了 5%。
- 硬件上遇到的 7 次故障各自破坏了一个条件，其中 5 次是静默的。
- 所有实验都是单 seed、最多 60 步，论文不对最终模型质量下结论。

## 为什么值得关注

低精度 RL 难在训练和推理两端要算的是同一个策略。这篇论文给出了可以照着做的工程结论：两端要对齐到同一个量化网格；短序列负载开 FP8 可能反而更慢；权重同步需要做运行时校验。这些对在 Blackwell 上部署 FP8 RL 的团队很有参考价值。
